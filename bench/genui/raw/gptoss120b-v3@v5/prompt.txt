Write the UI in GistUI: one statement per line, `id = value`.
Order: `root = …` first, then containers, then leaves, then data tables last.
- Component: `Name(positionals, children…, key:value)`. Required props are positional, in signature order
  (or named); optional props are always named, in any order.
- Enum values and flags are bare words: `variant:clear`;
  a boolean prop alone turns it on: `Card(a, b, wrap)`;
  an enum value alone sets the one prop that has it: `Card(a, b, sunk)`.
- Strings are JSON strings (use \n, no raw newlines). A string child is Markdown: `Card("### MRR", "**$412k**")`.
- Ids are short, lowercase and may be used before they are defined: `root = Card(head, body)`. Give ids to
  sections; write small parts inline where they are used: `Card(Tag("New"), Tag("Sale"))`.
- Tables are pipe rows; the first row is the header (`Rev:n` marks a number column) and the first
  column is the x axis or category. One table can feed HorizontalBarChart, RadarChart, PieChart, RadialChart, SingleStackedBarChart, AreaChart, BarChart, LineChart, Table:
  rev = |Month|Revenue
  |Apr|84500
  |May|87200
- Expressions: + - * / % == != < > <= >= && || ! a ? b : c, a.b, a[0], `@each(list, r => Card(r.name))`.

Types:
Content = TextContent|MarkDownRenderer|CardHeader|Callout|TextCallout|CodeBlock|Image|ImageBlock|ImageGallery|Separator|HorizontalBarChart|RadarChart|PieChart|RadialChart|SingleStackedBarChart|ScatterChart|AreaChart|BarChart|LineChart|Table|TagBlock|Form|Buttons|Steps
DialogContent = Content|Heading|Blockquote|InlineCode|Alert|Badge|Avatar|Progress|PaginationBlock|CalendarBlock|ListBlock|FollowUpBlock

Components (bare positional = text; `…X` = children of type X; bare trailing name = flag):
Root and layout:
  Card(...DialogContent|Tabs|Carousel|SectionBlock|DialogBlock|DrawerBlock|AlertDialogBlock, variant:card|sunk|clear, direction:row|column, gap:none|xs|s|m|l|xl|2xl, align:start|center|end|stretch|baseline, justify:start|center|end|between|around|evenly, wrap) — Styled container. variant: "card" (default, elevated) | "sunk" (recessed) | "clear" (transparent). Always full width. Accepts all Stack flex params (default: di
  Steps(...StepsItem) — Step-by-step guide
  StepsItem(title, details) — title and details text for one step
  Tabs(...TabItem) — Tabbed container
  TabItem(value, trigger, ...Content) — value is unique id, trigger is tab label, content is array of components
  Carousel(children:list, variant:card|sunk) — Horizontal scrollable carousel
  Accordion(...AccordionItem) — Collapsible sections
  AccordionItem(value, trigger, ...Content) — value is unique id, trigger is section title
  - Card is the root. Everything the user should see must hang off its children list, in reading order.
  - Tabs, Accordion and Steps take item references. Define each item on its own line instead of inlining them all in one statement.
  - Every slide of a Carousel must repeat the same component sequence.
Content:
  TextContent(text, size:small|default|large|small-heavy|large-heavy) — Text block. Supports markdown. Optional size: "small" | "default" | "large" | "small-heavy" | "large-heavy".
  MarkDownRenderer(textMarkdown, variant:clear|card|sunk) — Renders markdown text with optional container variant
  CardHeader(title?, subtitle?) — Header with optional title and subtitle
  CodeBlock(language, codeString) — Syntax-highlighted code block
  Image(alt, src?) — Image with alt text and optional URL
  ImageBlock(src, alt?) — Image block with loading state
  ImageGallery(images:list) — Gallery grid of images with modal preview
  Separator(orientation:horizontal|vertical, decorative) — Visual divider between content sections
  Heading(text, level:h1|h2|h3|h4) — Standalone heading
  Blockquote(text, cite?) — Quoted text with an optional citation
  InlineCode(code) — Inline code span
  - Name a section once. A CardHeader followed by a heading that repeats the same words is duplication.
  - MarkDownRenderer is for prose that carries its own structure; TextContent is for one short passage.
  - Use real, publicly reachable image URLs (e.g. https://picsum.photos/seed/KEYWORD/800/500). Never invent one.
Status and labels:
  Callout(variant:info|warning|error|success|neutral, title, description) — Callout banner. Optional visible is a reactive $boolean — auto-dismisses after 3s by setting $visible to false.
  TextCallout(title?, description?, variant:neutral|info|warning|success|danger) — Text callout with variant, title, and description
  TagBlock(tags:list) — tags is an array of strings
  Tag(text, icon?, size:sm|md|lg, variant:neutral|info|success|warning|danger) — Styled tag/badge with optional icon and variant
  Alert(title, description, variant:default|destructive|info|success|warning) — Alert banner with icon, title, and description
  Avatar(fallback, src?, alt?) — Avatar image with a text fallback
  Badge(text, variant:default|secondary|destructive|outline|ghost|link) — Small status or category badge
  Progress(value:num, label?) — Progress bar with an optional label
  - Callout, TextCallout and Alert carry a message that needs attention. Badge and Tag label a value in place and carry no message.
  - Status colors live on Tag (success, warning, info, danger), TextCallout (success, warning, info, danger), Callout (success, warning, info, error) and Alert (success, warning, info, destructive) variants. Badge and Button variants are visual styles from their signatures only: Badge has no success or warning, Button has no ghost.
  - Progress shows one value against its whole. Several values compared against each other belong in a chart.
Charts (2D):
  HorizontalBarChart(labels:list, ...Series, variant:grouped|stacked, xLabel:str, yLabel:str) — Horizontal bars; prefer when category labels are long or for ranked lists
  Series(category, values:list) — One data series
  RadarChart(labels:list, ...Series) — Spider/web chart; use for comparing multiple variables across one or more entities
  AreaChart(labels:list, ...Series, variant:linear|natural|step, xLabel:str, yLabel:str) — Filled area under lines; use for cumulative totals or volume trends over time
  BarChart(labels:list, ...Series, variant:grouped|stacked, xLabel:str, yLabel:str) — Vertical bars; use for comparing values across categories with one or more series
  LineChart(labels:list, ...Series, variant:linear|natural|step, xLabel:str, yLabel:str) — Lines over categories; use for trends and continuous data over time
  - A chart takes a pipe table: the first column holds the category-axis positions; each further column is one series, with a value in every row.
  - Pick by the question: compare categories, follow a trend over time, show accumulation, rank long-named categories, or compare several measures for a few entities.
Charts (1D):
  PieChart(labels:list, values:list, variant:pie|donut, appearance:circular|semiCircular) — Circular slices; use plucked arrays: PieChart(data.categories, data.values)
  RadialChart(labels:list, values:list) — Radial bars; use plucked arrays: RadialChart(data.categories, data.values)
  SingleStackedBarChart(labels:list, values:list) — Single horizontal stacked bar; use plucked arrays: SingleStackedBarChart(data.categories, data.values)
  Slice(category, value:num) — One slice with label and numeric value
  - These take a two-column pipe table, label and value, and show parts of one whole. They cannot show a trend.
Charts (scatter):
  ScatterChart(...ScatterSeries, xLabel:str, yLabel:str) — X/Y scatter plot; use for correlations, distributions, and clustering
  ScatterSeries(name, ...Point) — Named dataset
  Point(x:num, y:num, z:num) — Data point with numeric coordinates
  - Use a scatter plot for the relationship between two numeric measures. Each ScatterSeries is one named group of Points.
Tables:
  Table(...Col) — Data table — column-oriented. Each Col holds its own data array.
  Col(label, data:list, type:string|number|action) — Column definition — holds label + data array
  - A Table takes a pipe table: one row per entry, one cell per column in every row.
  - A handful of unrelated facts is not a table. Reach for one only when entries share the same fields.
Forms:
  Form(name, buttons:Buttons, ...FormControl) — Form container with fields and explicit action buttons
  FormControl(label, input:Input|TextArea|Select|DatePicker|Slider|CheckBoxGroup|RadioGroup, hint?) — Field with label, input component, and optional hint text
  Input(name, placeholder?, value?, type:text|email|password|number|url, rules:list) — Input
  TextArea(name, placeholder?, value?, rows:num, rules:list) — TextArea
  Select(name, ...SelectItem, placeholder:str, rules:list, value:str, size:small|medium|large) — Select
  SelectItem(value, label) — Option for Select
  DatePicker(name, mode:single|range, rules:list, value:list) — DatePicker
  Slider(name, variant:continuous|discrete, min:num, max:num, label?, step:num, defaultValue:list, rules:list, value:list) — Numeric slider input; supports continuous and discrete (stepped) variants
  CheckBoxGroup(name, ...CheckBoxItem, rules:list, value:list) — CheckBoxGroup
  CheckBoxItem(label, description, name, defaultChecked) — CheckBoxItem
  RadioGroup(name, ...RadioItem, defaultValue:str, rules:list, value:str) — RadioGroup
  RadioItem(label, description, value) — RadioItem
  Label(text) — Text label
  SwitchGroup(name, ...SwitchItem, variant:clear|card|sunk, value:list) — Group of switch toggles
  SwitchItem(name, label?, description?, defaultChecked) — Individual switch toggle
  CalendarBlock(defaultMonth?, mode:single|multiple|range, numberOfMonths:num, captionLayout:label|dropdown) — Inline calendar
  - Define EACH FormControl as its own reference. Do NOT inline every control in the Form statement.
  - A FormControl wraps exactly one input: Input, TextArea, Select, DatePicker, Slider, CheckBoxGroup or RadioGroup.
  - Form requires explicit buttons. Always pass a Buttons(...) reference as the second Form argument, and NEVER nest a Form inside a Form.
Buttons:
  Buttons(...Button, direction:row|column) — Group of Button components. direction: "row" (default) | "column".
  Button(label, action:list, variant:primary|secondary|tertiary, type:normal|destructive, size:extra-small|small|medium|large) — Clickable button
  - A Button with no action sends its label back as a user message, which is what most screens want.
  - Group related buttons in one Buttons reference rather than scattering loose Button references.
Collections:
  FollowUpBlock(...FollowUpItem) — List of clickable follow-up suggestions placed at the end of a response
  FollowUpItem(text) — Clickable follow-up suggestion; when clicked, sends text as user message
  ListBlock(...ListItem, variant:number|image) — A list of items with number or image indicators
  ListItem(title, subtitle?, actionLabel?, image:list) — List row with a title, optional subtitle and image
  SectionBlock(...SectionItem, isFoldable) — Collapsible accordion sections; use SectionItem for each section
  SectionItem(value, trigger, ...Content|ListBlock|FollowUpBlock) — Section with a label and collapsible content, used inside SectionBlock
  PaginationBlock(currentPage:num, totalPages:num) — Page navigation for long result sets
  - Use ListBlock when each entry is a title plus a line of detail. Use a table when every entry shares the same fields.
  - SectionBlock groups long content into collapsible sections; each SectionItem needs a unique value id and holds content components.
  - FollowUpBlock belongs at the very end and holds suggested next messages, not controls for the current screen.
Overlays:
  DialogBlock(triggerLabel, title, ...DialogContent, description:str, triggerVariant:default|destructive|outline|secondary|ghost|link) — Button that opens a modal dialog with content
  DrawerBlock(triggerLabel, title, ...DialogContent, description:str) — Button that opens a slide-out drawer with content
  AlertDialogBlock(triggerLabel, title, description, confirmLabel?, cancelLabel?, triggerVariant:default|destructive|outline|secondary|ghost|link) — Button that opens a confirm/cancel dialog
  - An overlay hides its content behind a trigger. Anything the user must see at a glance belongs on the screen itself.
  - AlertDialogBlock is for a confirm-or-cancel decision; DialogBlock and DrawerBlock hold arbitrary content components.

Example:
root = Card(CardHeader("Revenue Overview", "Last 30 days"), Tag("On track", success), Alert("Refund spike", "Refunds rose 14% week over week", warning), revenueSection, actions)
revenueSection = Card(Heading("Weekly revenue", h3), Table(kpisRows), LineChart(trendRows, natural, xLabel:"Week", yLabel:"USD"), sunk)
actions = Buttons(Button("Export CSV"), Button("Share report", secondary))
kpisRows = |Metric|Value
|Revenue|$128,400
|Orders|1,982
|Refunds|$3,120
trendRows = |Week|Revenue
|W1|24100
|W2|30800
|W3|34600
|W4|38900

Example:
root = Card(CardHeader("Book a demo", "Tell us about your team"), form)
form = Form("demo-request", formButtons, nameField, emailField, sizeField, planField)
nameField = FormControl("Full name", Input("name", "Jane Smith"))
emailField = FormControl("Work email", Input("email", "jane@company.com", email), "We only use this to reply")
sizeField = FormControl("Team size", sizeSelect)
sizeSelect = Select("team_size", SelectItem("1-10", "1-10 people"), SelectItem("11-50", "11-50 people"), SelectItem("51+", "51+ people"), placeholder:"Choose a range")
planField = FormControl("Interested plan", planRadio)
planRadio = RadioGroup("plan", RadioItem("Cloud", "Managed by us", "cloud"), RadioItem("Self-hosted", "Runs in your infra", "self"))
formButtons = Buttons(Button("Request demo", primary), Button("Cancel", tertiary))

Rules:
- Output only GistUI: no prose, no code fences.
- Define every id you use, once; do not define ids you do not use.
- Put chart and table data in pipe tables, not in arrays.
- Never pad optional props with null; omit them.
- Use only the components, props and enum values printed above. A prop exists only on the components whose signature lists it; never carry one over from a similar component.
- Leave optional props out unless the screen needs them; their defaults are good. When the value you want is not in a prop's list, omit the prop instead of guessing (there is no `primary` unless it is printed).
- The root children list is a COMPLETE commitment: every component you define MUST be reachable from root's children, directly or through a listed parent. A defined-but-unreferenced statement renders NOTHING and its content is silently missing from the final screen. Before writing root, enumerate every section you plan to emit; after writing everything, verify every defined variable is reachable from root. The most common mistake is defining a section heading, series or button and never listing it in any children or reference list; every name you define must appear in at least one.
- Required arguments are positional, in the order shown in each signature (or named, `key:value`); every optional argument is named (`key:value`), in any order. Never pass optional arguments positionally and never pad with null. Enum-typed arguments accept ONLY the listed values, exactly as written; never invent variants that are not in the signature.
- Enum lists are closed: a value that is not printed in the signature does not exist, even if other UI libraries use it. Before writing an enum value, check it appears in the signature; if the value you want is missing, use the closest listed value or omit the optional argument.

Reserved words (flags, never ids): decorative, defaultChecked, isFoldable, wrap

Before you finish, check: `root` comes first; every id you use is defined and every id you define is used; every component, prop and enum value appears in its signature.
